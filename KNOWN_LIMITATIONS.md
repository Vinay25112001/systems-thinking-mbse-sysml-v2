# Known Limitations

## Source audit
1. **Partial reading of very large documents.** About 52 % of the 4,892 PDF pages were read in full, about 24 % skimmed and about 23 % not opened (`SOURCE_INVENTORY.md` §2). The unread material is mainly OCL mapping rules (S07), formal abstract syntax and semantics (S05, S06), bibliographies, indexes and DoD acquisition chapters. Every topic-relevant knowledge area was read in full.
2. **Parallel readers.** 13 sub-agent readers produced the page-level notes. Seven key claims were re-checked by hand against the source text and all were confirmed, but not every citation in the notes has been independently re-checked. Each citation is re-verified when it is used in a lesson.
3. **Figures.** No system PDF renderer (pdftoppm) is installed. Pages were rendered with PyMuPDF where readers needed visuals (≈ 239 pages). The S08, S11 pp.724–1705 and S13 pp.1–363 readers saw **no figures**.
4. **The sources are beta, partly dated, and contain errors** (`SOURCE_ANALYSIS.md` §1, §5).
5. **No Air Taxi technical sources** exist in the collection, so all Air Taxi numbers are teaching assumptions (D5).

- Tested in Google Chrome only; axe checks found 0 WCAG 2 A/AA violations but automated checks do not prove full accessibility.
- Progress and maps live in localStorage: per browser, per machine, no accounts, no sync.

## Course server backend (M2, 2026-10-21; `learning-studio/docs/server/M2_BACKEND_REPORT.md`)
- **Local demonstration only (D1).** Binds 127.0.0.1, plain HTTP, synthetic accounts and data only (FD-S4). It is not deployed anywhere, has no TLS, and must not hold real student records before the university data-protection and IT review.
- **Development runner only.** The server runs through Vite's SSR loader (`node server/run.mjs`); there is no production bundle (`server:build`) and no served SPA build (`build:served`) yet. The SPA reaches the API through the Vite dev proxy.
- **`node:sqlite` is marked experimental in the Node 24 docs** (stated from memory); access is behind an async repository interface so `better-sqlite3` or PostgreSQL can replace it.
- **No institutional SSO, no email, no self-registration, no roster import.** Instructors create student accounts (temporary password shown once); admins create staff accounts.
- **Collaboration is polling (15 s), not live editing.** A teammate's overlapping edit of the same field, a retire/renumber of the same item, or any concurrent restore stops the save with "Conflict requires review"; the student keeps their unsaved edits as a version in History and loads the latest. There is no per-field conflict panel (Keep mine / Keep theirs / Keep both) yet.
- **The outbox lives in the tab's sessionStorage, not IndexedDB** (M2 review M4). Unsaved change sets survive a reload, an expired session and a sign-in in the same tab, and are re-sent with the version check; closing the tab (or the browser) still loses edits that were never saved, which is why the page warns before unload. Sign-in in place is a modal; it refuses a different account (the kept edits belong to whoever made them). There is no offline queue that keeps working while the server is down.
- **Which proposal fields are "material" to the approval is an integrator default awaiting faculty confirmation** (M2 review H1). The list is one constant, `APPROVAL_MATERIAL_FIELDS` in `learning-studio/src/project/model/approvalBinding.ts`: enterprise name, description and problem statement, the mission and objectives (MGO title/text), and the parts inside (PRT) and outside (EXT) the boundary. A material edit after approval is accepted but moves the approval to "approved, then changed" (the Week 1 readers then show "not approved"); going back to exactly the approved content restores it. The Week 1 lab tool itself does not yet name the "changed since approval" state (it shows "not approved"); that label belongs to the Week 1 rework (M4a/M6).
- **Restore and replace-import of an approved project do not ask first.** The material-edit warning is shown for edits in the editor; a restored or imported version that changes the proposal is handled by the server (re-review state) without a prior question.
- **Submissions, feedback and progress are not built** (M6; submissions and feedback were built in M6, see the M6 section below); content publishing is built in limited scope (M3, section below). The faculty store exists for one item: the instructor's private note on an approval decision (`approval_faculty_notes`, read only through an instructor context); lecture notes and answer keys join it in M3.
- **Snapshot quota** (M2 review M3): 200 versions and 50 MB per project, 1 MB per version (`server/config.ts` `SNAPSHOT_QUOTA`). Automatic and pre-restore versions are pruned first; then a new version is refused with a message to delete old versions. Labels stay free text (a student may still type "Milestone 1" into a manual version's label); the kind, the server's `rev` and the initials of who stored it are authoritative.
- **A member's own review clears an impact flag** (confirmation review N6, info): when a change set carries the member's `set-review` for an artifact, the server does not add the derived "needs review" flag for it. A member can reach the same state with "Mark reviewed", so this is not a bypass; a future rule that review must be a separate act would close it.
- **Signing in as a different account in the recovery dialog keeps the first account's outbox** in the tab (only an explicit sign-out clears it), so the person who made the edits can still sign in and save them; it holds project content, never credentials.
- **Instructor password reset can be used to act as a student** (M2 review L3, accepted for D1): the reset is audited and signs the student out, which makes it noticeable. For D2/SSO the reset becomes admin-only or student-confirmed.
- **No session rotation on a role or membership change** (M2 review L8, written deviation from `SECURITY_ARCHITECTURE.md` §4.2): authorization is recomputed from the database on every request, so a removed member loses access at once (tested); rotating the token would add no protection here.
- **The static student build still contains the sign-in and review UI chunks** (M2 review L9, accepted): code, not data (§6.2); with `VITE_BACKEND=none` they have no API path and never load.
- **The Week 1 lab tool still shows its self-declared approval select.** In server mode a change to it is refused with a message; the authoritative decision is the instructor's (My Project overview, "Enterprise approval").
- **Rate limits are in-process** (single process); restarting the server clears throttles, but not account locks, which are stored. An account lock lasts one hour (an admin may unlock sooner); behind a reverse proxy every student would share one IP, so a trusted-proxy setting and a shared limiter store are D2 work. Password change is limited to 5 attempts per session per 15 minutes and 10 wrong current passwords per account per hour; scrypt runs at most 2 at a time, sign-in ahead of password changes, and a full queue (64) answers "busy".
- **Browser data is never migrated automatically.** A student brings a browser project to the server only by creating the team project from a Week 1 file or an exported project file; Weeks 2–6 localStorage records are not migrated.
- **Backups are manual** (`npm run server:backup`); the daily/pre-migration/pre-restore schedule and retention pruning of `SECURITY_ARCHITECTURE.md` §12 are only partly automated (pre-migration and pre-restore copies are automatic).

## Content publishing (M3, limited scope per A24, 2026-10-21; `learning-studio/docs/server/M3_PUBLISHING_REPORT.md`)
- **Scope:** the course introduction (homepage text), the course settings (department label) and the 58 Week 1 Learn sections. Slides, faculty notes, lab, assessments, the Week 1 Overview and the Learn outline (section order) stay code-authored.
- **Read-only blocks:** definitions, tables, equations, worked steps, figures, interactive figures, attached footnotes, section titles and the homepage structure cannot be edited in the app; quotations in seed text must stay verbatim. Changing them is a developer edit of the TypeScript, which the store then flags as "Code changed" (it is never applied to the store automatically).
- **Two sources by design until cutover (FD-C1 not performed):** on the course server the store is authoritative; offline, on GitHub Pages and in the static student build students read the bundled TypeScript content. There is no `content:snapshot` export to the static edition yet.
- **Stale drafts** need an explicit acknowledgement after the compare view; the three-way view of the design is not built. **Plan tokens** are held in server memory (a restart invalidates open plans).
- **Self-review only** (FD-C2 default): an instructor may mark ready and publish their own draft; both steps are recorded. Admin accounts without the instructor role cannot author (404).
- **Separate migration track** for the content store (`content_schema_migrations`), a written deviation to avoid colliding with concurrent main-track migrations.
- **Student consumption needs a signed-in session**; signed-out visitors of the served app see the bundled content. "Updated since you read it" compares the browser's local read time with the publication time (server-side progress is M6).
- **One item per release in the UI** (the API accepts up to 100); no release revert; no raster upload; no instructor-entered references.

## My Project canvas, Excel import, approval and submission UI (M6, 2026-10-21; `learning-studio/docs/week1/M6_REPORT.md`)
- **The canvas edits the Week 1 parts through the existing record adapter** (`diffTeamRecord`): typed trace fields (need sources, concerns, objective) stay free text that is parsed into links; a token that does not resolve is kept as unresolved, never dropped. Moving a concern to another stakeholder is not offered (remove it and add it to the other stakeholder).
- **A25 changes the register gate on purpose:** the level of interest with a reason is required, influence and support are optional. A record exported before M6 without interest values is now "not ready" (the week1-model-inputs v3 status field), although its bytes are otherwise unchanged (golden test). Teams add the interest values in My Project.
- **The relationship map is read-and-select** (spec MP-22): nodes on a circle, no drag, no automatic layout for large registers; relationships are created from the table or the "Add relationship" form. The map shows stakeholders and REL rows only; conflicting concerns and need traces are listed in "All Week 1 relations".
- **Field guidance content is assembled from existing sources and course conventions; the faculty has not reviewed it.** Fields without an AeroLink example (suitability, AI statement, self-check, assumptions, unknowns) say so.
- **Progress shows course structural checks only.** It never claims the work is right; the enterprise description is a new M6 criterion (one sentence) that the earlier lab tool did not ask for.
- **Excel import:** .xlsx only; the reader is an in-repo SpreadsheetML reader on fflate 0.8.3 (MIT), not a general spreadsheet library: dates arrive as the stored serial numbers, merged cells and rich formatting are ignored, only the cached value of a formula is read (and flagged); text that looks like a formula (`=`, `+`, `-`, `@`) is kept as text and flagged; no spreadsheet or CSV export exists yet (one must prefix-escape such values). Parsing runs in a Web Worker with a 12 s hard stop (10 s reader deadline); without Worker support it runs in the page. On the course server every import change set gets a server-written `pre-import` version and an `import_records` row (file, SHA-256 when known, created IDs, change set, restore point); "Undo this import" restores exactly that version, and explains instead of restoring anything when it cannot be found. Undo is a whole-content restore: it asks first when the project changed since the import (a teammate's later edits would be removed too; they stay in History). The AI mapping provider is an interface only, disabled; no network call exists.
- **Duplicate detection** is name-based (normalised exact match, then word-set similarity ≥ 0.85, advisory): "County health department" and "County health dept", or "City permits office" and "City permit office", are not detected as duplicates (M6 review L-10, not fixed).
- **Approval:** request, approve, request revision and re-review exist; **withdrawing a pending request is not offered** (spec §f.2 lists it). Milestone `state` and `markedSubmittedAt` are still free member-writable fields on the server (pre-M6, M2; review L-11): nothing reads them as an approval or submission. In the browser-only edition the approval box says that approval happens on the course server; a decision typed into an earlier version of the lab tool is shown read-only as "not an approval". The material-edit confirmation (A26) is asked once per page load.
- **Submission (course server only):** Week 1 only. The validation summary the instructor sees is computed by the server from the frozen snapshot; the browser's own report is kept only to flag a difference. The submission names the revision the team reviewed and is refused (409) when the project changed meanwhile, or while the browser still has unsaved changes. Only "enterprise not named" and "proposal never sent for approval" block a submission. A resubmission supersedes an undecided or returned one; limits (review M-3): at most 10 submissions per project and week, an unchanged project cannot be resubmitted, and two submissions are at least one minute apart. Proposal and submission versions are permanent (database triggers refuse update, delete and replacing inserts; decisions are final) and are outside the members' version quota. Superseded submissions are kept but listed for the instructor only on request. No downloadable copy of the submitted snapshot yet (the instructor opens it read-only; the team sees version ID and fingerprint). Submission states are not mirrored into the project document; grades are not recorded in the app.
- **The earlier lab tool (Team enterprise view)** is no longer on the student route (the student edition redirects to the canvas); it stays in the instructor edition and in source.
- **Default-config e2e:** the M6 review found the earlier failures came from the shared dev server's stale optimizer cache (homepage, archive: `recharts` and `@xyflow/react` now pre-bundled) and from tests left stale by M4a/M5 (lecture gate, Guided Practice route, the `/week/1/examples` hand-off), now corrected; see M6_REPORT §7 for the run on a fresh private dev server.
- **Week 7 reads the v3 status:** a Week 1 record completed before M6 and re-exported now reads "not ready" there until interest values are added (WEEK1_CHANGE_IMPACT_MATRIX X9a; review L-5).
- **Guidance on narrow screens** (below 1200 px) opens as a bottom sheet from the (i) buttons (table cells included); focusing a field there does not open it (spec §f.5). Table-cell fields carry no `aria-invalid`; validation is given in the item's details and the guidance (review L-17, partly fixed).
