## Engineering method

1. **Purpose first.** Write one paragraph in the root package’s documentation: who uses the model, and for which decisions (at least 15 words). The purpose is what the model will be judged against; a valid model with no purpose cannot be judged. *(Taught in: Session 1, slide 8 ‘Model quality is not design quality’.)*
2. **Mapping matrix.** For every ID kind in your package (30 kinds in the course mapping), record the model package, the SysML v2 construct and the week that models it; mark the kinds modeled now and the kinds mapped for later. Give a reason for every choice that is not obvious, and choose a home for any kind the mapping does not cover. The choice is yours; the reason is graded. *(Taught in: Session 2, slide 8 ‘The import is a mapping, not a copy’; Session 2, slide 9 ‘The artifact-to-model mapping matrix’.)*
3. **Package skeleton.** Create the packages of the course structure (Context, Stakeholders, Needs, Requirements, Behavior, Logical, Physical, Verification, Analysis, AROU, Evolution), with private imports and a documentation line on every package that is still empty saying which week fills it. Every Phase I ID is a quoted short name, so the same ID names the item in the document and in the model. *(Taught in: Session 2, slide 2 ‘Packages, namespaces and qualified names’; Session 2, slide 3 ‘Imports and visibility’; Session 2, slide 4 ‘Names and short names: carrying the Phase I IDs’; Session 2, slide 5 ‘Comments, documentation and notes’; Session 2, slide 10 ‘The model’s package structure’.)*
4. **Context.** Model the enterprise as a part definition, and the context as a part that references the system of interest and holds every external system as a part usage with its ID. The elements inside the boundary of the system of interest become its part usages. *(Taught in: Session 1, slide 14 ‘The definition–usage pattern’; Session 2, slide 13 ‘AeroLink worked example I: the context’.)*
5. **Stakeholders and concerns.** Model every stakeholder as a part definition and every concern as a concern whose subject is declared first, followed by its stakeholder parameters typed by those part definitions. Carry the register ratings and reasons as assessment metadata, or keep them in documentation and say why. *(Taught in: Session 2, slide 11 ‘Stakeholders and concerns in SysML v2’; Session 2, slide 14 ‘AeroLink worked example II: stakeholders, concerns, ratings, relationships’.)*
6. **Stakeholder relationships.** Model each relationship of the register as a dependency tagged with the keyword of its type, written from the dependent stakeholder (the client, after from) to the stakeholder it depends on (the supplier, after to): a change to the supplier may require a change to the client. So “A regulates/funds/supplies B” becomes #regulatedBy/#fundedBy/#suppliedBy (in that order) from B to A; “A is affected by B” stays from A to B; the symmetric types (#partnersWith, #coordinatesWith, #conflictsWith) keep the register’s order. At least 3, at least 1 of them a conflict (a team of three: the conflict relationships only). *(Taught in: Session 2, slide 14 ‘AeroLink worked example II: stakeholders, concerns, ratings, relationships’.)*
7. **Import audit.** Answer the four audit questions (completeness, structure, fidelity, gaps) for your model, and give every gap, unmapped kind and defect a disposition: what you will do about it, and why. Differences between the register and the model are recorded, not fixed silently. *(Taught in: Session 2, slide 15 ‘AeroLink worked example III: auditing the import’.)*
8. **Checker to zero errors.** Install the course checker once per team from the install guide, run the tool proof first (the pass file and the fail file), then run model v0.1 through the course-designated checker and correct it until the checker reports no errors; explain every warning in the log. A PASS shows the file parsed, every name resolved and no rule fired; it does not show that the model says what your register says, which is why the audit comes before it. *(Taught in: Session 1, slide 24 ‘Predict the checker’; Session 1, slide 25 ‘Live demonstration: running the course checker’; Session 2, slide 6 ‘The course toolchain’; Session 2, slide 7 ‘What the checker decides, and what it cannot’.)*

## The lab tool

The lab tool imports your Week 1 model-inputs file (versions 1, 2 and 3) and, optionally, your Week 2 model-inputs file. It builds the mapping matrix, where you enter the counts of the Weeks 3–6 kinds and your reasons; lists the import findings by class, each with a field for its disposition; answers the completeness and structure questions of the audit from the record; and generates the model skeleton: the purpose, the Context and Stakeholders packages modeled, every later package with the week that fills it. Only a real defect keeps an item out of the model (a relationship whose end is not a registered stakeholder would not resolve); everything else imports and is reported. The tool’s checks are course acceptance checks: whether the model is valid is decided by the course-designated checker, and a checker PASS does not show that the model says what your register says. One member can export the workspace for teammates to continue. Everything is saved in your browser only, so export after every working session.

## Install and run the course checker

> The same guide, with download buttons for the course files, is on the Laboratory page (`#/week/8/lab/checker`).

The lab tool in this app is where your team writes model v0.1; it is the required environment. Whether a model is valid SysML v2 is decided by the course checker, which runs on a computer, not in the browser. So every team needs one working installation before Session 2: the team’s checker owner (normally the AI & Data Management lead) installs it from this guide, and the team runs every file on it. The lab machines are the fallback. Installing it on your own computer as well is optional: about an hour the first time, and not counted in the week’s hours.

The course checker is the OMG SysML v2 Pilot Implementation, release 2026-08 (the implementation published with the SysML v2.1 Beta 2 texts this course cites), run by a small course script. It parses each file, resolves every name against the file and the standard library, and runs the pilot implementation’s validation rules. An ERROR fails the file; a WARNING does not. A PASS shows only that the file parsed, every name resolved and no rule fired: it never shows that the model says what your register says. It runs offline once installed, and nothing you check is uploaded.

```
OMG SysML v2 Pilot Implementation (SysMLInteractive, Jupyter kernel jar) release 2026-08 (kernel 0.62.0), Java 21.0.12.1+1-LTS, library load … s
PASS  (expected PASS: OK)  models/tool_proof_pass.sysml

```

Your paths and the library load time will differ; the PASS and FAIL lines and the diagnostic must not.

### Reading the output

- **First line.** The tool, its release (2026-08) and kernel (0.62.0), and the Java version. If the release is not 2026-08, you installed a different pilot implementation: grades follow the 2026-08 release.
- **PASS (expected PASS: OK).** The file parsed, every name resolved and no rule fired. The expectation comes from the file name: a file named invalid_… is expected to fail, any other file to pass.
- **FAIL (expected FAIL: OK).** At least one ERROR. For the tool-proof fail file this is the right result.
- **ERROR 9:12 mismatched input ….** Severity, line:column, message. Go to that line and column; a syntax error is often reported a token or two after the real mistake, so read the start of the line and the line before it too. One mistake can cause several errors further on: fix the first one and run again.
- **WARNING ….** Reported, but the file still passes. Read it anyway (a duplicate name usually means two elements got the same ID or name), and explain each warning in the checker log.
- **Summary line.** Counts of PASS, FAIL and ERROR, and where the JSON report was written. ERROR in the count (not in a diagnostic) means the tool itself failed on that file: see troubleshooting.

### Troubleshooting

| Symptom | What to do |
|---|---|
| “SysML reference validator is NOT installed; no file was validated.” | The script lists each missing part and the exact path where it looked. Compare with the folder layout: usually jdk-21 or sysml-pilot-2026-08 is misnamed, or the kernel was unpacked one folder too deep or too shallow (the jar must be at tools/sysml-pilot-2026-08/kernel/sysml/jupyter-sysml-kernel-0.62.0-all.jar). |
| `python` is not recognized, or opens the Microsoft Store (Windows) | Install Python 3 from python.org (tick “Add python.exe to PATH”), open a new PowerShell window, or use `py -3` in place of `python` in every command. |
| “portable JDK 21 (javac)” is missing | You downloaded a JRE. Download the JDK archive (its name contains “jdk”, not “jre”) and repeat step 2. |
| macOS: “jdk-21/bin/java: No such file or directory” | The macOS archive keeps Java inside Contents/Home. Move jdk-21.0.12.1+1/Contents/Home to tools/jdk-21, as in step 2. |
| The checksum differs from the one in the guide | Delete the file and download it again. If it still differs, do not use it: tell the teaching assistant. |
| “Compiling the launcher failed” | SysMLBatchCheck.java is missing, misnamed (for example SysMLBatchCheck.java.txt) or not in checker/scripts/sysml-launcher. Save it again from this page. |
| “No such file or directory: …” | Run the command from the checker folder (step 5 starts with cd), and name the file with the models/ folder in front. |
| A download is blocked or very slow on the campus or company network | Use another network, or run your files on your team’s installation or a lab machine; tell the teaching assistant before Session 2. |
| “The SysML tool did not produce trustworthy results; NOTHING is reported as PASS.” | Run the command once more. If it happens again, keep the full output and use the team installation or a lab machine while the teaching assistant looks at it. |
| Windows: the unpack command ends in a Traceback (FileNotFoundError), often on a file under sysml.library | The folder path is too long for Windows. Delete tools\sysml-pilot-2026-08, move sysml-checker higher up, for example C:\sysml-checker, adjust the paths in the commands and unpack again. A part-unpacked library can still start the checker, so never skip this. |
| Your own model FAILS | That is not an installation problem: the checker is working. Read the first ERROR, fix that line and run again. The fail file of the tool proof shows what a correct FAIL looks like. |

**Fallback.** No working installation by Session 2? Run the two tool-proof files on your team’s installation, or on a lab machine at the Session 2 checkpoint, and keep both outputs for the log. A team with no working installation at all books a fix with the teaching assistant before day 3 of the lab: the final checker run is part of the submission.
