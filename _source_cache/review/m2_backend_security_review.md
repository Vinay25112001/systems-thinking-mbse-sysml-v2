# M2 course server: independent security and data-integrity review

Reviewer: independent agent (read-only, adversarial). Date: 2026-10-21.
Scope: the uncommitted M2 work. This covers `learning-studio/server/**`, `src/services/{backend,httpProjectAdapter}.ts`, `src/auth/*`, `src/project/model/serverRules.ts`, the M2 diff in `src/project/store/*`, `src/project/transfer/*`, `vite.config.ts`, `package.json`, `.gitignore` and `.env.student`, and the backend section of `KNOWN_LIMITATIONS.md`.
Design references: `SECURITY_ARCHITECTURE.md` (§4–§7, §12), `PROJECT_DATA_SCHEMA.md` (§2, §5.2, §6.2), and directive §6, §7, §12.4 and §15.
Out of scope: Week 6, the Week 1 M4a rework and lectures.

## Verdict: **REVISE (targeted)**

The security layer is sound and I would sign it off. That layer covers authentication, sessions, CSRF, the Host/Origin checks, the `authorize()` choke point, IDOR protection and the non-leakage of `private_note`. I found no Critical issue and no authN/authZ bypass. Every cross-team and cross-role probe I ran returned the required 404 or 403.

Revision is still needed for one High finding and a group of Medium findings, all in **data integrity**, not access control:

- An approval stays valid after the student replaces the approved enterprise (H1).
- The server does not run `commitOps`, so derived integrity operations can be left out (M1).
- Forged `before` values are stored in the authenticated history (M2).
- Snapshots are stored unvalidated and without any quota (M3).
- An idle-expired student loses unsaved edits when signing back in (M4).

Fix H1, M1, M2 and M4 before sign-off. M3, M5 and M6 can be scheduled, but must be listed in `KNOWN_LIMITATIONS.md` if they are deferred.

## Questions in the brief, answered

- **scrypt:** N=2^17, r=8, p=1, 16-byte salt, 64-byte key, self-describing string. Confirmed in the throwaway DB (`scrypt$v=1$N=131072,r=8,p=1$…`). `timingSafeEqual` is used. An unknown account burns a dummy scrypt of the same cost. Measured on the live server: known/wrong 213–231 ms, unknown 210–224 ms, with an identical 401 body. A lower N is accepted only with `SLS_MODE=test` (`config.ts:91`).
- **Lockout variants:** `normLogin` applies NFC, trim and lower-case before every limiter key and lookup. `"  TSA.X  "` signs into `tsa.x`, so case and whitespace variants cannot bypass the per-login counters. The (login, IP) pair delay was verified: the correct password right after 5 failures gets 429.
- **Sessions:** the token is 32 random bytes in base64url (43 characters), and only its SHA-256 is stored (64-hex rows confirmed). The cookie is `HttpOnly; SameSite=Strict; Path=/; Max-Age=absolute`, with `__Host-` and `Secure` in institutional mode. A new session is created on every login and the old presented one deleted, so no fixation is possible. Idle expiry was enforced (401 after 2 h + 1 s); absolute expiry is in `sessionState`. Logout deletes the row (reuse gets 401) and leaves other sessions live. Password change revoked the other session (401) and issued a fresh one.
- **CSRF:** every POST/DELETE requires `application/json` (415 otherwise), an allow-listed Origin (or Referer), and for authenticated routes `X-SLS-CSRF` matching the hash of this session's token. The token of another session gave 403. Login is protected by JSON plus Origin (login CSRF closed). There are no GET routes with side effects except `last_seen_at` touching and the instructor export audit row. Host allow-listing blocks DNS rebinding (bad Host gives 400).
- **AuthZ:** every route declares an action, and `app.ts:135-146` loads the resource and calls `authorize()` before the handler. Over 18 cross-team probes (project, changes, export, snapshots, snapshot by id, approval, team, writes, project creation, approval request, users, queue, audit, team creation, self-add), a student of another team got 404 every time. The instructor got 403 on changes, snapshot create and delete, approval request and project creation. Instructors cannot create admins or reset admin passwords (403). An admin without the instructor role cannot see projects or approvals (404).
- **private_note:** the marker string was absent from all 13 student-reachable responses: project, changes, approval, export, snapshot list, every snapshot, teams, team, session, the queue (404), and a 409 conflict body. It was present for the instructor, and absent from the audit log. It does live in the same DB file and backup copy (M5).
- **Input:** streaming body limits work (413 for 2 MB, per-route limits). Bad JSON gets 400. `__proto__`, `constructor` and `prototype` keys are refused anywhere in a body, with a depth limit of 24 and caps on string and list sizes. All SQL is parameterised; `VACUUM INTO` paths are quote-escaped. There is no static file serving (non-`/api` paths get 404), so no path traversal. The `Content-Disposition` file name is reduced to `[A-Za-z0-9-]`. 500 responses are generic, with no stack trace, SQL or path.
- **Concurrency:** one connection, an in-process mutex plus `BEGIN IMMEDIATE`, and AsyncLocalStorage so that reads inside a transaction reuse it. The version check happens in the same transaction as the update (`UPDATE … WHERE version = ?`). Parallel writes on the same base gave `[200, 409]`. A replayed `clientChangeId` gave 200 `replayed:true` with no new version. Approval decisions are atomic (`WHERE state='pending'`); a second decision gets 409. Replace and restore keep server-owned approval and members (the probe returned approval empty and milestone approval null). Import is non-destructive: create only, with a `pre-import` snapshot, and replace keeps identity, history and counters.
- **Backups:** online `node:sqlite backup()` under the mutex, with pre-migration and pre-restore copies via `VACUUM INTO`, a manifest with SHA-256 per file, and an integrity check after restore (see L7 for the edge cases).
- **Frontend:** "Saved" is set only after `saveProject` resolves with the server's document (`ProjectStore.write` and `create`). Offline mode is labelled "Saved in this browser only". The CSRF token is held in memory only, and there is no `localStorage`/`sessionStorage` use in `src/auth`, `src/services` or `src/project/store`. Retries reuse the same `clientChangeId` (WeakMap per ChangeSet), so they are idempotent. There are no `dangerouslySetInnerHTML` sinks in the new UI.
- **Ops:** the default data directory is `%LOCALAPPDATA%\SysMLStudio\data`. The server refuses a data directory inside the repository or a synced folder, refuses non-loopback binding outside institutional mode (verified with `netstat`: `127.0.0.1:51873 LISTENING`), and refuses institutional mode while demo accounts exist. Vite binds 127.0.0.1:5173 with `changeOrigin:false`. `.gitignore` covers `.data/` and `server/.env` (verified with `git check-ignore`). Seed prints the passwords once and only to stdout. A grep of the diff and all new files for password literals, keys and temporary-password patterns found only test fixtures with obvious wrong-password strings. No `.db` or pid files are untracked in the repository.

## Residual risks for a future institutional host (D2)

- **Rate limits behind a reverse proxy:** the IP is taken from `req.socket.remoteAddress` (`app.ts:103`) and no trusted-proxy setting exists. Behind a proxy, every student shares one IP, so 30 login attempts per minute across the whole class can lock everyone out, and the per-IP layer becomes useless. Add a trusted `X-Forwarded-For` setting and a shared limiter store for multi-process deployments.
- **Login enumeration:** move the lock message to the generic form (L5), and consider CAPTCHA or SSO instead of password login. SSO also removes L3.
- **Missing browser hardening:** HSTS and served-SPA CSP are absent. In dev the API sends a CSP but the SPA is served by Vite. A `build:served` with the §9 headers is required.
- **Backups:** `sls.db` copies hold password hashes, faculty notes and all student work in plaintext under `%LOCALAPPDATA%`. D2 needs encrypted, retention-pruned, access-controlled backups, and scheduled backups (currently manual).
- **`node:sqlite`:** it is a single connection and the mutex serialises every request, which limits throughput for a class-sized load. The module is experimental in Node 24. A move to PostgreSQL must preserve the transaction-scoped version check, the `IMMEDIATE` semantics and the idempotency uniqueness.
- **Shared computers:** a signed-out browser falls back to IndexedDB, and the previous user's local project stays readable to the next person at that computer.
- **Audit log:** append-only triggers exist, but `prev_hash`/`hash` chaining is unimplemented, so an administrator with file access can rewrite history undetectably.
- **Staff power is not limited by the server:** instructor password resets (L3) and instructor membership edits (adding any student to any team) can give access to a team project.
